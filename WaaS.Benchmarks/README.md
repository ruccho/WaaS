# WaaS / xLua / Lua-CSharp benchmark

This directory compares the load time and the execution time of WaaS with those of [xLua](https://github.com/Tencent/xLua), a binding to the native Lua implementation, and [Lua-CSharp](https://github.com/nuskey8/Lua-CSharp), a Lua 5.2 interpreter implemented in C#. It measures non-development Windows x64 players built with Unity, on both the Mono and the IL2CPP scripting backends.

## Requirements

- Windows
- Unity 6000.5.8f1 with the Windows Build Support (IL2CPP) module. Set the `UNITY_EDITOR` environment variable to use an installation outside of the default Hub directory.
- Python 3
- Rust with the `wasm32-unknown-unknown` target, and `wasm-tools`
- `wit2waas`, only for regenerating the bindings

## Usage

```
python run.py all                  # build, measure and report
python run.py build                # download xLua, build the guest and the players
python run.py bench --cold-runs 15 # measure and report
python run.py report               # report the existing results
python run.py bindings             # regenerate Assets/Benchmark/Bindings from guest/wit
```

`--backend mono` or `--backend il2cpp` limits the commands to one backend. Results are written to `results/`, and the summary to `results/report.md`. xLua and Lua-CSharp are downloaded at the commit and the version pinned in `run.py`, and are not stored in this repository. `Assets/csc.rsp` loads the source generator of Lua-CSharp from `unity/Tools`.

## Contents

| Path | Description |
|---|---|
| `guest/` | Workloads in Rust, compiled to a WebAssembly component |
| `lua/benchmark.lua` | The same workloads in Lua, shared by xLua and Lua-CSharp |
| `unity/` | Unity project containing the harness |
| `run.py` | Setup, build, execution and reporting |

## Method

Each workload exists in Rust and in Lua, and returns a checksum. The harness stops with an error when the checksums of the implementations differ.

Load time is measured by stage. `engine-init` is the creation of `LuaEnv`, or of `LuaState` with the standard libraries. WaaS has no corresponding stage. `load` is `Component.Create`, `LuaEnv.LoadString` or `LuaState.Load`. `instantiate` is `IComponent.Instantiate` or the execution of the Lua chunk. `first-call` is the first call of a script function. File reading is not included.

- The first load in a process is measured in a separate process for each sample, and includes JIT compilation on Mono. Each process runs only one engine.
- The repeated load is measured 30 times in one process, after 3 discarded runs.
- `xLua (bytecode)` loads a chunk precompiled with `string.dump`. Lua-CSharp 0.5.8 does not implement `string.dump`, so it loads the source only.

Execution time is the median of 15 samples, after 3 discarded runs. Garbage is collected between samples, outside of the measured time.

| Group | Description |
|---|---|
| `compute_*` | Workloads that do not cross the script boundary |
| `ffi_*` | The script calls a host function 100,000 times. The functions take no value, integers, a string, a string as the result, a `Vector3`-like struct, and a method of a host object. |
| `callback_*` | The host calls a script function 100,000 times |

The configuration is chosen to represent each engine in its usual production form.

- The guest is built with `opt-level = 3` and LTO. WaaS uses its default settings, without fuel or a debugger.
- xLua uses wrappers generated by its code generator, not reflection. `Vector3` is passed through its GC-optimized path. The Lua workloads cache host functions in locals.
- Lua-CSharp 0.5.8 from NuGet uses `[LuaObject]` bindings generated by its source generator, and calls scripts through its stack API, which does not allocate an argument array. It has no value type for host structs, so `ffi_struct` allocates a `[LuaObject]` class for each vector.
- The Windows x64 native library of xLua at the pinned commit is Lua 5.3, which is an interpreter. xLua's releases provide no Windows x64 library for LuaJIT, so LuaJIT is not measured. `lua/benchmark.lua` avoids Lua 5.3 specific syntax so that it can be run on LuaJIT with a library built separately.

The Rust workloads use the standard library, as a script in a product would. For example, `compute_map` uses `HashMap` with its default hasher on the guest side, and the table implemented in C on the Lua side.

## Results

Measured on 2026-11-02 with WaaS 0.4.0 (`9865183`), xLua `59bf426`, Lua-CSharp 0.5.8, Unity 6000.5.8f1, and an Intel Core i7-13700F on Windows 11. The script sizes are 39,255 bytes for the component, 3,978 bytes for the Lua source and 10,377 bytes for the xLua bytecode.

Values vary between runs on the same machine. Between two runs, some call benchmarks differed by up to about 2 times, so small differences should not be interpreted.

### Observations

- xLua is the fastest in every execution workload of this set, on both backends.
- WaaS is faster than Lua-CSharp in pure computation dominated by arithmetic and calls: about 7 to 8 times in `fib`, and about 1.8 to 3.9 times in `mandelbrot`.
- On Mono, WaaS is also faster than Lua-CSharp in `sieve` and `strings`. On IL2CPP, Lua-CSharp is faster in these, and in `sort` and `map` on both backends.
- Lua-CSharp is faster than WaaS in every call across the script boundary, about 1.2 to 10 times on IL2CPP.
- Lua-CSharp loads the fastest on IL2CPP. WaaS has the slowest load on both backends, and most of the load time is spent in `Component.Create`.
- All compute workloads of WaaS except `fib` are slower on IL2CPP than on Mono, while Lua-CSharp is faster on IL2CPP in every workload. The cause has not been investigated.
