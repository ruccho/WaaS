# WaaS / xLua benchmark

This directory compares the load time and the execution time of WaaS with those of [xLua](https://github.com/Tencent/xLua). It measures non-development Windows x64 players built with Unity, on both the Mono and the IL2CPP scripting backends.

## Requirements

- Windows
- Unity 6000.5.8f1 with the Windows Build Support (IL2CPP) module. Set the `UNITY_EDITOR` environment variable to use an installation outside of the default Hub directory.
- Python 3
- Rust with the `wasm32-unknown-unknown` target, and `wasm-tools`
- `wit2waas`, only for regenerating the bindings

## Usage

```
python run.py all                  # build, measure and report
python run.py build                # download xLua, build the guest and the players
python run.py bench --cold-runs 15 # measure and report
python run.py report               # report the existing results
python run.py bindings             # regenerate Assets/Benchmark/Bindings from guest/wit
```

`--backend mono` or `--backend il2cpp` limits the commands to one backend. Results are written to `results/`, and the summary to `results/report.md`. xLua is downloaded at the commit pinned in `run.py` and is not stored in this repository.

## Contents

| Path | Description |
|---|---|
| `guest/` | Workloads in Rust, compiled to a WebAssembly component |
| `lua/benchmark.lua` | The same workloads in Lua |
| `unity/` | Unity project containing the harness |
| `run.py` | Setup, build, execution and reporting |

## Method

Each workload exists in Rust and in Lua, and returns a checksum. The harness stops with an error when the checksums of the two implementations differ.

Load time is measured by stage. `engine-init` is the creation of `LuaEnv`, and WaaS has no corresponding stage. `load` is `Component.Create` or `LuaEnv.LoadString`. `instantiate` is `IComponent.Instantiate` or the execution of the Lua chunk. `first-call` is the first call of a script function. File reading is not included.

- The first load in a process is measured in a separate process for each sample, and includes JIT compilation on Mono. Each process runs only one engine.
- The repeated load is measured 30 times in one process, after 3 discarded runs.
- `xLua (bytecode)` loads a chunk precompiled with `string.dump`.

Execution time is the median of 15 samples, after 3 discarded runs. Garbage is collected between samples, outside of the measured time.

| Group | Description |
|---|---|
| `compute_*` | Workloads that do not cross the script boundary |
| `ffi_*` | The script calls a host function 100,000 times. The functions take no value, integers, a string, a string as the result, a `Vector3`-like struct, and a method of a host object. |
| `callback_*` | The host calls a script function 100,000 times |

The configuration is chosen to represent each engine in its usual production form.

- The guest is built with `opt-level = 3` and LTO. WaaS uses its default settings, without fuel or a debugger.
- xLua uses wrappers generated by its code generator, not reflection. `Vector3` is passed through its GC-optimized path. The Lua workloads cache host functions in locals.
- The Windows x64 native library of xLua at the pinned commit is Lua 5.3, which is an interpreter. xLua's releases provide no Windows x64 library for LuaJIT, so LuaJIT is not measured. `lua/benchmark.lua` avoids Lua 5.3 specific syntax so that it can be run on LuaJIT with a library built separately.

The Rust workloads use the standard library, as a script in a product would. For example, `compute_map` uses `HashMap` with its default hasher on the guest side, and the table implemented in C on the Lua side.

## Results

Measured on 2026-11-02 with WaaS 0.4.0 (`9865183`), Unity 6000.5.8f1, and an Intel Core i7-13700F on Windows 11. The script sizes are 39,255 bytes for the component, 3,810 bytes for the Lua source and 10,074 bytes for the Lua bytecode.

### Load (ms)

| | WaaS Mono | xLua Mono | WaaS IL2CPP | xLua IL2CPP |
|---|---:|---:|---:|---:|
| First load in a process | 105.3 | 35.3 | 12.2 | 6.9 |
| Repeated load | 5.4 | 0.9 | 4.7 | 1.4 |
| Load without engine init, first | 105.3 | 4.1 | 12.2 | 0.9 |

### Compute (ms)

| Workload | n | WaaS Mono | xLua Mono | WaaS IL2CPP | xLua IL2CPP |
|---|---:|---:|---:|---:|---:|
| fib | 30 | 109.7 | 65.3 | 92.1 | 50.1 |
| sieve | 1,000,000 | 284.7 | 49.7 | 466.6 | 65.5 |
| mandelbrot | 200 | 81.3 | 56.4 | 156.1 | 72.7 |
| strings | 20,000 | 361.3 | 42.3 | 388.9 | 38.8 |
| sort | 200,000 | 349.4 | 72.1 | 566.2 | 76.7 |
| map | 500,000 | 628.9 | 9.2 | 949.4 | 12.8 |

### Observations

- xLua is faster than WaaS in every workload of this set: about 1.4 to 2 times in `fib` and `mandelbrot`, about 5 to 10 times in `sieve`, `strings` and `sort`, and about 70 times in `map`.
- Calls across the script boundary are about 10 to 90 times slower in WaaS.
- The first load of WaaS on Mono is about 105 ms, and about 12 ms on IL2CPP. The difference between the first and the repeated load suggests that JIT compilation of WaaS itself accounts for most of the cost on Mono.
- The component is 39 KB, about four times the size of the Lua bytecode. The relation between the component size and the load time has not been measured.
- `sieve` and `sort` are slower on IL2CPP than on Mono, while `fib` is faster. The cause has not been investigated.
